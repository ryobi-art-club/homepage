# 設計の判断

なぜこういう作りなのかを知りたいとき、「ここは変えてよいか」を判断したいときに読みます。主な判断とその理由、試してやめた方法を残しています（同じことをもう一度試して、同じところでつまずかないように）。

## 構成と公開

| 判断 | 理由 |
|---|---|
| 管理画面は GAS、サイトは静的ファイル（GitHub Pages） | 費用をかけず、サーバーの管理をしなくて済むため。データはスプレッドシートと Drive に置き、部員がふだん使う Google のサービスの中で完結させている |
| 試すための別の環境（本番の複製）は作らない | スプレッドシート・Drive・GAS・GitHub App をもう一組用意して保つ手間が、部活のサイトには見合わないため。代わりに、管理画面もサイトも手元でサンプルデータを使って再現できるようにしている（`cms/tools/preview/`・`tools/screenshot/`） |
| サイトの作り直しは、管理画面からの公開かワークフローの手動実行だけ | 部員が内容を確かめてから出せるようにするため。そのため、日付が来たら自動で何かを変える仕組み（終了した展示会の自動アーカイブなど）は入れていない。入れるなら、定期実行のワークフローを足す必要がある |
| 管理画面と公開サイトを1つのリポジトリにした（2026年11月） | 2つが同じデータの約束（保存する内容の形・更新履歴）でつながっていて、片方だけを見て直すと壊しかねないため。1回のコミットで両方と資料を一緒に直せ、引き継ぐ人が見る場所も1か所になる。反映（GAS と GitHub Pages）は今も別々 |

## 内容・画像と画面

| 判断 | 理由 |
|---|---|
| 画像は、一時置き場と退避先を使う（4種類とも） | 下書きを保存したり画像を外したりしても、公開中のサイトや別の下書きの画像が壊れないようにするため。使わなくなった画像を直接削除せず退避先に残すことで、公開が途中で止まっても、再公開で画像の移動をやり直せるようにしている |
| 退避先の画像は、次の公開が成功したらゴミ箱へ | 退避先が要るのは、公開が途中で止まったときのやり直しのためだけ。公開すると下書きも消えるので、退避先の画像を管理画面から使い直す方法はない。取り戻すのは Drive のゴミ箱からでも同じなので、退避先に長く置かない |
| 地図は埋め込まず、住所を Google マップへのリンクにした | 以前の埋め込み用の URL は Google の正式な方法ではなく、いつ使えなくなるかわからなかった。埋め込みはページが重く、スマホではスクロールの邪魔にもなる。部員が URL を用意する手間もなくなった |
| 会期表示は開始日・終了日から自動で作る | 同じ日付を2回入力していて、片方だけ直すと食い違っていたため。日付で書けない会期のために手入力も残し、日付を変えたら自動に戻す、という単純な決まりにしている |
| 古い画面からの公開は、元の公開内容と世代を照合して止める（2026年11月） | ロックだけでは、後から届いた古い内容での上書きを防げない。通し番号だけではシートの復旧で以前と同じ番号になるため、内容そのものと、シートの復旧で戻らない世代も使う。下書きは退避のため保存を許し、元の基準を保つ。自動統合はせず、競合時は入力を控えて最新内容へ変更を入れ直す |
| 公開した内容は `_PublishedState` に JSON で1か所だけ置く | 2026年10月までは、同じ内容を `Recruit`・`ActivityArticles`・`Exhibitions`・`RequestCases` の4枚のシートにも表の形で書いていた。二重持ちで食い違いの元になるのでやめた。人が表で見たくなっても、表のシートを足し直すのではなく、JSON から作る方法を考える |
| 管理画面を開くときは、シートを Sheets API で1回にまとめて読む | SpreadsheetApp はシート1枚につき4回ほど問い合わせるので、1枚ずつ読むと、画面を開く8秒のうち7秒がシートの読み込みだった（2026年10月）。GAS の「サービス」の Sheets（`appsscript.json` の `enabledAdvancedServices`）を使っている。UrlFetchApp で Sheets API を直接呼ぶ方法は、API が有効になっておらず失敗したので使っていない |
| 公開では、前回から変わった項目の Drive だけを処理する | 全部の項目のフォルダと画像を毎回確かめていたころは、変更のない公開でも約2分かかり、内容が増えるほど遅くなっていた（2026年10月） |
| サイトのビルドは、前回取得した画像をキャッシュに残して使う | ビルドの時間のほとんど（3分のうち2分40秒。2026年10月）が Drive からの画像の取得だったため。公開リポジトリのキャッシュは外から読めるので、今のサイトに載っている画像だけを入れる（[画像のキャッシュ](reference/site.md#画像のキャッシュ)） |
| 文字の大きさはデジタル庁の基準に合わせた | 日本語は同じ大きさでも英語より読みにくいため。読みやすさと押しやすさ（押せる部分は44px以上）を優先した |
| 管理画面の画像は、誰でも見られるものだけ Drive から直接読む | 画像の `<img>` は、見ている人のブラウザが自分のアカウントで Drive に取りに行く。非公開のフォルダの画像は、閲覧権限のないブラウザでは見えない（2026年10月に、部員のブラウザで新歓・活動記録・ご依頼の画像が見えないことがわかった）。そこで公開中の項目のフォルダは誰でも見られる設定にし（画像はもともとサイトに載っている）、それ以外はサーバーが管理画面を実行する権限で取って渡す |
| 右側のプレビューは、ボタンを押したときだけ作る | 画像の一覧を取るたびに GAS の処理が走るため。必要なときだけにして、待ち時間と負担を減らした |
| 毎回は読まない説明は「？」でたたむ | 画面を広く使うため。部員向けの使い方の説明は画面の中に置き、別のマニュアルで画面を二重に説明しない |
| 部員向けのマニュアルは作らない（2026年11月にヘルプページもやめた） | 画面の見本を含むマニュアルは、画面を変えるたびに直す必要があり、内容が古くなりやすかった。ヘルプページもほとんど読まれず、管理者が直接答えていた。画面の中の「？」と、管理者への相談（[部員からよく聞かれること](troubleshooting.md#部員からよく聞かれること)）で足りている |
| 公開すると全員の下書きが消える | 公開した内容と古い下書きが食い違ったまま残るのを防ぐため |
| ページのタイトルと説明文は短いままにする | Bing Webmaster Tools は「短い」と指摘するが、その目安（50〜60字）は英語の文字数。言葉を詰め込むと、検索のための言葉を並べただけの文に見えるので、部の名前と内容が素直に伝わる今の文にしている（2026年11月） |

## ログインと外部連携

| 判断 | 理由 |
|---|---|
| Gemini は Google AI Studio の無料枠の API キーで使う | 費用をかけないため。無料枠では送った内容が Google の改善（学習）に使われることがあるが、送るのは目録と、サイトに公開する文章だけで、どのみち公開するものなので問題ないと判断した |
| エラーは3段階で見せ、システム側の問題は管理者に通知する | 画面の1行に収めつつ、部員が管理者に正確に伝えられるようにするため |
| SheetJS は公式 CDN から、版を固定し整合性チェック付きで読む | 一般的な CDN（cdnjs）の SheetJS は古い版で止まっていて、既知の脆弱性があるため。版を固定しているので、更新は手で行う（[定期的な点検](operations.md#定期的な点検)） |
| スプレッドシートには「書式なしテキスト」で書く | 数式や日付として解釈されるのを防ぐため（数式の注入対策でもある） |
| ログインは Google アカウントに加えて確認コードを使う | 管理画面はデプロイしたユーザーの権限で動く設定なので、見ている人のメールアドレスを GAS から知ることができない。そこで、入力されたアドレスにコードを送り、そのメールを受け取れた人を本人とみなしている（[管理画面の仕組み の「`AppAuth.js` — ログイン」](reference/cms.md#appauthjs--ログイン)） |
| 許可リストは、内容のシートとは別のスプレッドシートにした | 内容のシートは基本的に人が見ないもの、許可リストは人が見て編集するもの、と役割が違うため。共有の範囲も分けられるので、内容の編集とは別に、ログインを許可する人を管理できる |
| 管理画面の URL はリポジトリに書かない | 入口を外の人に知られにくくするため。部員に直接伝える |
| スクリプト プロパティには、秘密の値・作り直すと変わる ID・メールアドレスだけを置く | GAS の画面ではプロパティが名前の順に並ぶだけで、数が多いと見づらかった。ほかの設定は2種類に分けている。管理画面を動かしながら変えることがある値（ログインの有効期限、Gemini のモデル、片付けの止め方）は `AppConfig.js` の `CONFIG_DEFAULTS` に今の値を書き、同じ名前のプロパティで上書きできるようにする。デプロイのときに変えればよい値（リポジトリ名、確認コードの有効期限など）は、ほかの決まった数字と同じく使うファイルの先頭の定数にし、上書きはできない（どれを本番中に変えてよいかが分かるように）。上書きを長く続けるなら、`CONFIG_DEFAULTS` を同じ値に直してプロパティを消す（既定の値と実際の値がずれると、どちらが本当か分からなくなるため） |
| サイトのビルドの起動は GitHub App だけで行う | 以前は個人のアクセストークン（Fine-grained Personal Access Token）も選べたが、作った人の個人のものなので引き継げず、有効期限もある。2つの方式があると混乱するので、2026年11月に GitHub App だけにした。App は組織に所属するため、作った人の個人のトークンに依存せずに使える。起動に使うトークンは毎回、短時間だけ有効なものを作る |

## 開発と運用

| 判断 | 理由 |
|---|---|
| 手元で確かめるのは、管理画面もサイトもサンプルデータだけ | 本物のデータを読みに行くと重く、崩れやすい場合（長い文、画像のない項目など）を網羅的に見られないため。サンプルデータにはそうした場合をわざと入れ、本物のデータや Google の権限（鍵）も手元に置かずに済む。Google から読む部分は、偽物を使うテストで確かめる。2026年11月に、サイトを本番のデータで手元でビルドする手順もやめ、管理画面とそろえた |
| バックアップは年2回、手で書き出して Google の外に置く | 元の保存先にアクセスできなくなっても、文章と画像を失わないため。手で書き出す方法なら、自動で控えを取る仕組みやその権限を増やさずに続けられる。頻度は年2回と、管理者が交代するときにしている（2026年11月） |
| リポジトリは公開し、ライセンスは付けない | 工夫を見てもらえるように公開している。ライセンスを付けると、ふつうは「使ってよい」と許可を出すことになるので付けず、著作権の表示だけを書いている（[著作権](../README.md#著作権)）。公開してはいけないものは、コミットの前とプッシュのたびに確かめる（[開発の環境を整える（最初に1回）](development.md#開発の環境を整える最初に1回)） |
| ホームページ固有の資料は公開し、IT係共通の管理手順は非公開の手引きにまとめる | ホームページの仕組み・設計理由・開発・運用手順を1か所で読めるようにし、共通するアカウント管理・権限の受け渡し・復旧手順の二重管理を避けるため。公開側は必要な権限と確認方法を説明し、実際の担当者やアカウントの所有関係を列挙しない。ホームページ固有の説明は、公開に必要なものを残し、不要なものは削る。非公開の手引きには共通手順だけを置く |
| Node.js・Python の版を管理する道具（anyenv・nodenv・pyenv など）は使わない | Windows では WSL を入れる必要があり、後任の準備の手間に見合わないため。[開発の環境を整える（最初に1回）](development.md#開発の環境を整える最初に1回) の「動作を確かめた版」に合わせれば足りる |
| ブランチやプルリクエストは必須にしない | 触る人が少なく、慣れていない人でも作業できるようにするため。`main` に直接 push してもテスト（`check.yml`）は動き、サイトは「公開する」まで変わらない |
