# 管理者の手順（運用・引き継ぎ・点検）

ホームページを運用する管理者が、ふだんの作業・引き継ぎ・年1回の点検をするときに読みます。

## 新しい管理者の確認事項

アカウントと権限の引き継ぎは、IT係の手引きで確認します。このページでは、ホームページの管理に必要な確認を行います。前の管理者が対応できるうちに、上から順に確かめます。

1. [Apps Script](https://script.google.com/) で、`cms/.clasp.json` の `scriptId` と一致するプロジェクトを開き、「デプロイ」→「デプロイを管理」で本番のデプロイと管理画面の URL を確認できる。
2. 管理画面にログインできる。
3. 許可リスト用スプレッドシートを編集できる。
4. GitHub でリポジトリの設定と Actions の実行結果を確認でき、最近のサイトのビルドが成功している。
5. [バックアップ](#バックアップを取る) の置き場所と、控えから戻せる範囲を確認した。
6. このページの [放っておくと止まるもの](#放っておくと止まるもの) と [定期的な点検](#定期的な点検) に目を通した。
7. [開発の環境を整える（最初に1回）](development.md#開発の環境を整える最初に1回) を最後の確認まで終えた。固定の文章や画像を変更するためにも、この準備が要ります。

## ふだんの運用

### 部員を追加する・外す

1. 許可リスト用スプレッドシートを開き、`allowlist` シートに1人1行で書く。
   | name | email |
   |---|---|
   | 部員の名前 | メールアドレス |
2. 外すときは、その人の行を消す。

**確かめ方**：追加した人に管理画面を開いてもらい、確認コードのメールが届いてログインできれば完了です（登録されていないアドレスにも「送りました」と出るので、メールが届くかで確かめます）。

- `name` は、管理画面の「ログイン中」や公開履歴に表示されます。
- 外した人も、すでにログイン中なら、ログインの有効期限（[Script Properties（設定値）](reference/cms.md#script-properties設定値) の `SESSION_TTL_MINUTES`）が切れるまで使えます。
- 管理画面のログインは「Google アカウントでのログイン」と「確認コード」の2段階です。Google アカウントは何でもよく、許可リストに載っているかどうかは確認コードを送るメールアドレスで判定します。

### 年度替わりにすること

- [ ] 許可リストを更新する（新しい担当者を追加、卒業生を外す）
- [ ] 管理画面の「入部希望の方」で、新しい年度を追加する
- [ ] 管理者が交代するなら、[新しい管理者の確認事項](#新しい管理者の確認事項)を行う
- [ ] [バックアップを取る](#バックアップを取る)
- [ ] [定期的な点検](#定期的な点検)をひととおり行う

### エラーの通知メールが届いたら

システム側のエラー（設定の不備、GitHub との連携の失敗、Google の利用上限など）は、スクリプト プロパティ `ERROR_NOTIFY_EMAIL` に設定した宛先へ通知されます。部員が画面からコピーして送ってくる報告文も、同じ形式です。

1. メールの「操作」と「内容」を見て、[困ったとき（症状から探す）](troubleshooting.md)の表で原因を探します。
2. 詳しい記録は、GAS エディタの「実行数」画面にあります（エラーは `console.error` で記録されます）。日時とエラー ID で探せます。
3. 「公開」のエラーでも、**内容はスプレッドシートに保存済み**のことが多いです（GitHub の起動だけが失敗した場合など）。原因を直したら、もう一度「公開する」を押せば反映されます。

### バックアップを取る

年2回と、管理者が交代するときに、次のものを書き出し、Google の外に保存します。Google の外に置く理由は [設計の判断](decisions.md)。

1. コンテンツ用スプレッドシート：「ファイル」→「ダウンロード」→「Microsoft Excel（.xlsx）」
2. 許可リスト用スプレッドシート：同じ
3. Drive の4つのルートフォルダ：Drive でフォルダを右クリック →「ダウンロード」（zip になる）

- 保存するフォルダの名前に日付を付けます。新しい Excel と画像の zip を開き、必要な文章と画像が入っていることを確かめます。前回の控えは、その確認まで消しません。
- 許可リストには部員のメールアドレス、`_AdminLog` シートには公開した人のメールアドレスが入っています。個人情報として扱い、リポジトリには入れません（[公開してはいけないものの確認](development.md#公開してはいけないものの確認)）。
- **控えから自動で元に戻す仕組みはありません。** Drive に画像を上げ直すとファイルの ID が変わり、`_PublishedState` に保存した ID と合わなくなるためです。控えは作品の画像と文章を失わないためのもので、戻すときは [一から作り直す手順](setup.md) で作り直し、管理画面から入れ直します。

文章は、コンテンツ用の Excel の `_PublishedState` にある `payload_json` の JSON に入っています。複数セルに分かれている場合は、[データの約束](reference/data.md) の「下書きと公開内容の保存形式」を参照してください。

### Drive の容量

管理画面のホームに「Drive容量」が出ます。残りが少なくなると、色が変わり、容量を空けられる候補（古い展示会のフォルダなど）が表示されます。

- 削除した項目のフォルダや、展示会で使わなくなった画像は、公開のたびに自動で片付けます（[Google Drive のフォルダ構成](reference/cms.md#google-drive-のフォルダ構成)）。片付けたものは Drive のゴミ箱に入り、30日間は元に戻せます。ゴミ箱の中のファイルも容量に数えられるので、容量が空くのは30日後です。
- 容量は、管理画面を実行する Google アカウント全体の容量です。このシステムで扱う画像だけの合計ではありません。

### 固定の文章や画像を変える

管理画面で編集できないもの（紹介文、活動場所、年間スケジュール、画材、連絡先、SNS など）を変える手順です。どこを直すかは、下の表で探します。

1. `src/site_static.json`（画像なら `src/` のファイル）を直す。
2. [変更を確認して送る](development.md#変更を確認して送る) の手順で、見本データでの表示確認を済ませ、変更したファイルをコミットして push する。
3. [公開サイトを反映する](development.md#公開サイトを反映する) の手順で、ワークフローを手動実行する（push だけでは作り直されません）。

**確かめ方**：数分後にサイトを開き、直した所が変わっていれば完了です。

**公開後に間違いに気づいたとき**：同じファイルを修正して、上の手順でもう一度反映します。表示や動きのコードに不具合があるときは、[公開サイトのコードの変更を取り消す](development.md#公開サイトのコードの変更を取り消す) を参照してください。

| 内容 | 編集する場所 |
|---|---|
| 展示会・活動記録・新歓カレンダー・ご依頼事例 | 管理画面 |
| 部の名前、トップの見出し、紹介文 | `site_static.json` の `club_name_jp`、`hero_…`、`intro_text` など |
| 各タブの説明文 | `site_static.json` の `exhibitions_static.summary` など |
| 入部希望の方：基本情報・画材・年間スケジュール | `site_static.json` の `recruit_static` |
| ご依頼の方：連絡先 | `site_static.json` の `requests_static` |
| SNS のリンク、コピーライト | `site_static.json` の `social_links`、`copyright` |
| ロゴ、部室の写真 | `src/logo.png`、`src/clubroom.jpg` |
| デザイン・動き | `src/stylesheet.css`、`src/site.js`、`scripts/sitebuild/`（[公開サイトの見た目や動きを変えるとき](development.md#公開サイトの見た目や動きを変えるとき)） |

#### `site_static.json` の項目

| 項目 | 内容 |
|---|---|
| `club_name_jp` / `club_name_en` | 部の名前（日本語・英語） |
| `hero_kicker` / `hero_title` / `hero_subtitle` | トップの小見出し・見出し・説明 |
| `og_url` | サイトの正式な URL（SNS で共有したときの表示、検索エンジン向けの情報、sitemap に使う） |
| `og_image` | SNS で共有したときの画像（`logo.png` または URL） |
| `intro_text` | 紹介文 |
| `information_text` | INFORMATION の説明文 |
| `exhibitions_static.summary` / `activities_static.summary` | 展示会・活動記録タブの説明文 |
| `recruit_static` | 入部希望の方タブ。`headline`（見出し）、`summary`（説明）、`info_points`（基本情報）、`materials`（画材・道具）、`annual_schedule`（年間スケジュール） |
| `requests_static` | ご依頼の方タブ。`summary`、`contact_email`、`contact_instagram`、`contact_x` |
| `social_links` | `instagram` / `x` / `email` |
| `copyright` | フッターの著作権表示 |

**`recruit_static` の中身**

- `info_points`：`label`（項目名）と `text`（内容）の並び。写真を付けるときは `image`（`src/` に置いたファイル名）、地図などへのリンクを付けるときは `link`（`url` と `label`）を足す。
- `materials`：`name`（画材の名前）と `note`（説明）の並び。
- `annual_schedule`：`period`（時期）、`label`（内容）、`accent`（色：`yellow` / `blue` / `green` / `white`）の並び。

**文章の中のリンク**：`hero_subtitle`、`intro_text`、`information_text`、各タブの `summary`、`info_points` の `text` では、`[表示する文字](https://example.com)` と書くとリンクになります。

#### 写真を増やすときの注意

`src/` の画像は、ビルドの最後に `build_site.py` が**ファイル名を指定して** `dist/` にコピーしています（`STATIC_FILES` の `logo.png`、`clubroom.jpg`）。写真を増やしたら、ここにも名前を足してください。足さないと、サイトで画像が表示されません。

### 検索エンジン（Search Console・Bing）

ページは1枚だけなので、ふだんすることはありません。年に1回くらい、検索に出ているかを見る程度で足ります。

次の警告は出たままですが、**直さなくてよいもの**です。

- **Search Console のサイトマップが「取得できませんでした」のまま**：サイトを作ったときに `sitemap.xml` を送ってから、ずっとこの表示です。ページは検索に出ている（インデックスされている）ので、困ることはありません。
- **Bing Webmaster Tools の「タイトルが短い」「説明文が短い」**：わざと今の文にしています（[設計の判断](decisions.md)）。文は `scripts/sitebuild/page.py` の `SITE_TITLE`・`SITE_DESCRIPTION` です。
- **Bing Webmaster Tools の「`<img>` に ALT がない」**：ページ先頭のスライドの写真を、飾りとして空（`alt=""`）にしているのが原因と見ています（確かめてはいません）。飾りの画像は空にするのが正しい作りです。

## 放っておくと止まるもの

管理者がいない時期があっても、公開サイトは前の状態のまま表示され続けます。ただし、次のものは時間がたつと止まります。

| 止まるもの | いつ | 止まるとどうなるか | 直し方 |
|---|---|---|---|
| Gemini のモデル | 提供が終わったとき | 目録の読み取りが失敗する。誤字チェックはされずに公開される（公開そのものはできる） | [定期的な点検](#定期的な点検) の「Gemini のモデル」 |
| GitHub Actions の部品、Node.js・Python の版 | サポートが終わってしばらくすると、ワークフローで使えなくなる（2026年11月の時点で、ワークフローの Node.js 24 は2028年4月、Python 3.12 は2028年10月にサポートが終わる） | サイトのビルドが失敗し、「公開する」を押してもサイトが変わらない | [外部のライブラリや道具の版を上げるとき](development.md#外部のライブラリや道具の版を上げるとき) |
| Drive の容量 | 画像が増え続けて、いっぱいになったとき | 画像を追加できなくなる | [Drive の容量](#drive-の容量) |

### 更新を入れるかの判断

| 場合 | どうするか |
|---|---|
| 使っているものに脆弱性（セキュリティの穴）が見つかった | このシステムでの使い方に関係するなら、すぐ上げる。特に気にするのは、部員が選んだファイルを読む SheetJS と、サービスアカウントの鍵を扱うサイトのビルドで使う Python のライブラリ |
| サポートの終わりが決まった（Node.js・Python・GitHub Actions の部品・Gemini のモデル） | 終わる日より前の点検で上げる |
| 新しい機能が出ただけ | 上げなくてよい。上げるなら、年1回の点検でまとめて |

## 定期的な点検

年度替わりなど、1年に1回くらいを目安に確認します。

| 項目 | 確認すること | 方法 |
|---|---|---|
| SheetJS（Excel の目録の読み込み） | 脆弱性の知らせや、新しい版が出ていないか | [cdn.sheetjs.com](https://cdn.sheetjs.com/) を見る。上げ方は [外部のライブラリや道具の版を上げるとき](development.md#外部のライブラリや道具の版を上げるとき) |
| Font Awesome（アイコン） | 古すぎないか | 管理画面とサイトの両方で 6.4.2 を使っている。上げ方は同上 |
| Gemini のモデル | 提供が終わっていないか | 目録の読み取りや誤字チェックが「モデルが見つからない」などで失敗したら、スクリプト プロパティ `GEMINI_MODEL` に新しいモデル名を書く（すぐ効く）。次にコードを直すときに、`AppConfig.js` の `CONFIG_DEFAULTS` も新しい名前にして、プロパティは消す |
| Python のライブラリ（サイト側） | 大きな版上げや脆弱性の知らせが出ていないか | `requirements.txt`。上げ方は [外部のライブラリや道具の版を上げるとき](development.md#外部のライブラリや道具の版を上げるとき) |
| GitHub Actions の部品、Node.js・Python の版 | 古い版の警告が出ていないか、サポートの終わりが近くないか | Actions の実行結果の警告を見る。上げ方は同上 |
| サイトのビルド | 最近のビルドが成功しているか | GitHub の「Actions」。失敗していたら [困ったとき](troubleshooting.md) の「公開したのにサイトが変わらない」 |
| Drive の容量 | 残りが少なくないか | 管理画面のホーム |
| 検索エンジン | サイトが検索に出ているか | [検索エンジン（Search Console・Bing）](#検索エンジンsearch-consolebing) |

## アカウントと権限

引き継ぎ時や権限の問題が起きたときに、必要な項目を確認する一覧です。ふだんの作業は [ふだんの運用](#ふだんの運用) を参照してください。アカウントの管理・交代・復旧は、IT係の手引き（非公開）で確認します。

> **このリポジトリは公開されています。** 具体的なアカウント名・メールアドレス・パスワード・鍵は、ここには書かないでください。管理画面の URL も部員に直接伝え、リポジトリには書きません。

| 対象 | 誰に必要な権限か | 確認先 |
|---|---|---|
| GAS プロジェクト・管理画面の URL | 管理者：プロジェクトの編集・デプロイ | `cms/.clasp.json` の `scriptId` で対象を照合し、「デプロイを管理」で本番のデプロイと URL を確認する |
| コンテンツ用シート・Drive の4つのルートフォルダ | 管理画面の実行ユーザー：編集。サイトのビルド用サービスアカウント：閲覧 | スクリプト プロパティ `CONTENT_SPREADSHEET_ID`・`ROOT_…_FOLDER_ID` で対象を確認し、共有設定を見る |
| 許可リスト用シート | 部員を追加・削除する管理者：編集 | `ALLOWLIST_SPREADSHEET_ID` で対象を確認し、共有設定を見る |
| Google Cloud プロジェクト | 管理者：サービスアカウント・鍵の作成と管理 | Google Cloud Console の「IAM と管理」→「サービス アカウント」 |
| Gemini の API キー | 管理者：キーの作成と管理 | Google AI Studio と、スクリプト プロパティ `GEMINI_API_KEY` |
| GitHub リポジトリ | 管理者：コードの書き込み、ワークフローの実行、Pages とシークレットの設定 | リポジトリの「Settings」と「Actions」 |
| GitHub App | 管理者：App の設定・インストール管理。App：対象リポジトリの `Actions: Read and write` | App の設定・インストール先と、スクリプト プロパティ `GH_APP_ID`・`GH_INSTALLATION_ID`・`GH_PRIVATE_KEY` |
| Google Search Console・Bing Webmaster Tools | 管理者：対象サイトの管理権限 | 各サービスで対象サイトを開く。所有確認用のファイルは `src/verification/` |

### 管理画面を実行する権限

管理画面は「デプロイした人」の権限でシートや Drive を操作し、確認コードのメールも送ります（`appsscript.json` の `executeAs: USER_DEPLOYING`）。デプロイするアカウントを変えるときは、GAS プロジェクトと対象のスプレッドシート・Drive フォルダに必要な権限を設定し、新しいアカウントの権限でデプロイし直します。

- 管理画面の URL が変わった場合は、部員に新しい URL を直接伝えます。リポジトリには書きません。
- サイトのビルド用サービスアカウントへの共有も確認します。共有が外れると、ビルドが失敗します。
